# GameSpice Sim design

## What it is

Native (Rust, GDExtension) twins of hot script code in the Gamespice family, one module per job. Each module has a script original that stays the specification and the fallback: the game chooses at run time with `ClassDB.class_exists`, and the suite holds the two to the same answers. Nothing in a game may need gs-sim to run.

## Precision

The native code must give the bit-identical answer, not a close one, or a bot's choices drift from the script's over a match. The rules:

- `Vector3` is f32; its `length` is `sqrt` of `x*x + y*y + z*z` in f32, its `angle_to` is `atan2(|a x b|, a . b)` in f32.
- Script floats are f64: `rad_to_deg` multiplies by `180 / PI` in f64, and score arithmetic happens in f64 then rounds once to f32 when stored in a `PackedFloat32Array`.
- No fused multiply-add and no reordering: the Rust spells each expression in the engine's order.

## The bots boundary

Measured first (cp-orange-x3, 31 bots, headless on the build machine, per frame at 50 fps): the bot brain is 1.6 ms of a 5.7 ms game tick; inside one think call, perception is 27 µs of which the sight scan (`_candidates`) is 14 µs, hearing 14 µs, the fight 18 µs. The brain is no longer the dominant cost, so the native ceiling for bots is about 1.3 ms per tick, and the first kernel is the one pure, allocation-heavy loop: the sight scan.

- The game bumps `GSBotWorld.contacts_version` once per tick (game-fatal-contact sets it to the tick number).
- The first bot to think in a tick packs the bodies once into `GSSimBotSenses` (ids, aim points, teams, alive; struct of arrays).
- Each bot's scan is one call returning candidate indices; the scores and the "visible target died" flag are read after. The brain maps indices back to its `GSBotContact` list, so everything after the scan is unchanged script.
- `GSBotWorld.native_enabled` (static) switches it off for the suite and for comparisons; a world that never bumps the version always uses the script.
- GameSpice Bot names the class only as a `StringName` for `ClassDB`, so GameSpice Bot does not depend on GameSpice Sim.
- A brain thinking on a worker thread (game-fatal-contact's `bot_threads`) stays native: before the workers start it takes a handle on this tick's packed scan (`GSSimBotMind.hold_senses`) and perceives over it (`perceive_held`), so workers never touch the shared senses. Desktop and server builds bind with godot-rust's thread-safe storage (`experimental-threads`) and report `worker_safe()`; the web build is single-threaded, so there a worker brain moves into script.
- Games expose the switch as a setting (game-fatal-contact: cvar `bot_native`, on by default); without the library it is script either way.

| Run | Script | Native |
| --- | --- | --- |

## The snapshot boundary

`GSSimSnapshotCodec` is one behaviour's declarations (kinds, bits, ranges, pads) and two calls: `encode(values, changed, pad)` writes a state exactly as `GSNetBehaviour._encode` does, and `decode(bytes, pad)` reads one exactly as `read_state` does. GameSpice Net drives it through `GSNetSimCodec`; GameSpice Net names the class only as a `StringName` for `ClassDB`, so it does not depend on GameSpice Sim.

- Any value the script writes differently (a custom codec, a string, a 40-bit float range, a value of the wrong type) makes that state's encode fall back to the script; on decode the codec stops with `SCRIPT`, the script reads that one value, and the native read continues.
- A fixed-length float32 array (`GSNetVar.of_length(n)`, `PACKED_FLOAT32`, GameSpice Net API 20) is the codec's: a whole-array flag, then each float as its 32 bits, with signalling NaNs quieted as the script's float conversions quiet them. An older GameSpice Net never sends that kind; an older GameSpice Sim reads it as custom and leaves it to the script.
- Only the main thread encodes natively; snapshot workers keep the script.
- Off with `GSNetConfig.sim_codec` (`GS_NET_SIM_CODEC=0`, `--net-sim-codec=false`) or `GSNetSimCodec.enabled`; the web never loads it.
- GameSpice Net's own C++ core (`GSNetConfig.native`) already encodes on the server, so the codec matters there only with that core off; on a client it is the decode.

`examples/snapshot_selftest.tscn` holds it: 4000 random states encoded by both at every pad, every packet plus cut-short and noise packets decoded by both, and five scripted three-peer games (22 and 33 Hz, 10-20 % seeded loss, duplicates and jitter, interest rings, workers) whose payloads and received values must hash the same. The crate's `golden_player_state` test pins the bytes of one FC-like state, and `golden_packed_float32` those of a packed float array.

### From the packet to the interpolation buffers

On a client with `GSNetConfig.snapshot_batch` and `sim_interp` on, a snapshot goes from bytes to the interpolator without a script dictionary per entity:

1. `GSSimSnapshotBatch` (behind GameSpice Net's `GSNetSnapshotBatch`) decodes every changed entity's state in one call and pushes the decoded values straight into `GSSimInterpolator` (`push_list`: values in wire order, keyed by the interpolator's interned property names). The unchanged entities go in as one `push_repeat(ids, tick)`.
2. The interpolator's buffer is one ring per entity of `TRACK_CAPACITY` (32) samples; a sample is `(tick, [(key, value)])`, the key an index into the interpolator's name table, the value the crate's opaque value type (numbers and vectors blended in Rust, quaternions and colours in the engine). Nothing outside the crate reads the ring directly.
3. Readers ask the interpolator by net id, never the buffer: `sample` and `apply`/`apply_all` draw, `value_at(id, property, render, cut)` and `value_between(id, property, from, to, render, cut)` read a property without drawing (lag compensation, the view-target ease), `samples(id)` returns the whole track as `[{tick, values}]` oldest first, `newest_tick(id)` and `track_len(id)` answer without copying. A Rust module in gs-sim (remote-player presentation) borrows the rings through `GSSimInterpolator` in the same library rather than a copy; a script reader goes through `GSNetInterpolator.track_samples`, `newest_tick`, `has_track`, which answer from the script tracks or the native ones, whichever hold them.
4. `GSNetConfig.sim_interp_tracks_only` (off by default) drops the script's mirror tracks: GameSpice Net then keeps the samples only in the native interpolator. A game turns it on only once it no longer reads `GSNetInterpolator._tracks` (FC reads through `track_samples`; its `cl_interp_script_tracks 1` launch option brings the mirror back). Without the library (the web) the script tracks are the only ones whatever the setting.

gs-net's `netcode_demo` (snapshot batch parity) holds the native-only run to the script interpolator and to the mirrored one: the same samples, applied positions, baselines, hook ticks, newest ticks, `value_at`/`value_between` reads and whole tracks.

## Measured: snapshot (build machine, headless)

| Run | Script | Native codec |
| --- | --- | --- |
| 128 player states, encode (suite bench) | 9.91 ms | 2.81 ms |
| 128 player states, decode and apply (suite bench) | 11.15 ms | 3.22 ms |
| GameSpice Net `snapshot_bench`, server send ms per tick per client, 32/64/128 peers, GameSpice Net core off | 0.76 / 1.04 / 1.62 | 0.63 / 0.97 / 1.60 |
| the same with GameSpice Net's native core on | 0.17 / 0.27 / 0.41 | 0.17 / 0.25 / 0.42 |

With GameSpice Net's core off, a server's send is mostly per-pair bookkeeping, not encoding; with it on, the codec is not on the server's path. The win is the client's decode, about 3.5 times faster.

## Shipping

The libraries are built per platform (linux, windows, macos; x86_64 and arm64) by CI and shipped as release-asset zips, never committed ([native-ci.md](native-ci.md)). A dedicated server unpacks the zip for its platform at the project root (or builds with `ci/install.sh`) and imports once so the engine lists the extension. Web exports do not carry them (the dlink web build is opt-in and not shipped, [web.md](web.md)), so the web build and its size gate are untouched.

Sight LOD (GameSpice Bot API 25): `GSSimBotMind.set_sight_lod(far, far_reuse)`, `GSSimBotSenses.load_positions` and `sight_cached_far(id, now, stamp, reuse)` give the native mind GameSpice Bot's `sight_far` rule: a "not seen" about a body farther than `far` (f32 squared distance from the eye to the feet, never the current target) is held `far_reuse` s instead of `SIGHT_REUSE`. `sim_selftest` plays the same fight in script and native with it on (same intents, same ray count) and measures the saving: 24 bots thinking every third tick among 80 pillars, rays 29830 to 19853 (-33%), wall -20% with a free ray. A library without these methods keeps the plain reuse; GameSpice Bot checks with `class_has_method`.
